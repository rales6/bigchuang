三、从寻物转交近距接近的唯一有效条件

新增树莓派发布包：grasp_range_integration/phase1/verified_search.py。
它不能仅看进程退出码 0，因为原寻物执行器“正常检查完但没有找到”也可能返回 0。必须同时满足：
  1. 输出目录为本次启动后新建，位于 search_runs/ble_scene_17/ 下，不能复用旧成功任务；
  2. mission.json 原始指令一致、硬件模式为实车、result=success、有 finished_at；
  3. 最终 supervisor_directive=report_success；
  4. 最后一次 observation_complete 的 complete_cameras 同时为 left/right、dual_camera_confirmed=true；
  5. 同一 stereo_pair_id 两个检测都在请求工作区，类别/来源/颜色/边界框完整性校验均通过；
  6. 左右原图真实存在且不是同一文件。
  7. 同一合格双摄对的框中心和垂直差满足原追踪器起始接收视野，左右各留15像素余量；边缘双摄虽可作为寻物线索，但不能提前交接，须在原观察站小角度复拍。
通过后写 phase1_verified_handoff.json，字段 object_range_established=false、arm_grasp_authorized=false。也就是说：地图寻物仅授权进入下一段新鲜视觉追踪，绝不把双摄框冒充米制距离或直接授权机械臂动作。失败则非零退出，网页任务保持 blocked，不启动后段。
网页桥接另核对**本轮寻物进程的日志**是否宣布同一任务 ID/指令/目录的交接，拒绝复用旧成功记录。追踪启动后，被动证据记录位于 track/final_work/logs/handoff_evidence/<本轮追踪日志名>/handoff_evidence.json：包含第一阶段左右原图路径、最多三张追踪服务 JPEG、每帧服务状态和 /ground 日志摘要。旧框仅供诊断，视觉追踪仍须用新帧识别。记录器不控制底盘或机械臂，不能代替现场实车验收。

树莓派网页桥接与反向隧道现由 `final-work-pi-bridge.service`、`final-work-pi-tunnel.service` 开机自启，源配置位于本发布包 `track_web_integration/pi/systemd/`。检查：`systemctl status final-work-pi-bridge.service final-work-pi-tunnel.service --no-pager`；健康检查：`curl http://127.0.0.1:8780/health`。3090 网页仍由其自身服务提供；若未运行，可在3090执行 `cd /home/sjtu/track && bash final_work/run_3090_background.sh`。启动网页服务本身不执行任务。实车运行前检查电源、雷达、双摄、蓝牙、玻璃墙与前方通道；现场人员可以急停。网页输入“去柜子边上夹取一个红色的小物块”，检查计划含“地图寻物、视觉追踪、模型夹取、抓取核验”，再确认并自动推进。仅在现场允许运动时执行；不要用旧 car1.0 手动寻物命令与网页任务同时运行。

已知边界：目前自动链能够“规划地点→寻物确认→视觉接近→示教区微调→执行模型夹取动作”，但最后实物抓取成功需人在网页确认；抓取后搬运/放置不在本轮范围。其他物品可用目标描述重新识别中心，但应逐类实测尺寸和抓取高度，不能把红块模型的训练误差当成通用成功保证。
